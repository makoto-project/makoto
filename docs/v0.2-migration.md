# Migrating from Makoto v0.1 to v0.2

v0.2 is intentionally not wire-compatible with v0.1. Existing v0.1 schema URLs and examples stay
available as historical material; their bytes must not be silently relabeled as v0.2 evidence.

| v0.1 concept | v0.2 replacement |
|---|---|
| one mutable `lineage` array | one immutable signed statement per origin or transformation |
| hash labeled as a signature | strict DSSE v1 envelope with Ed25519 signature |
| signer string | cryptographic key ID plus receiver-owned authorization policy |
| source hash plus step descriptions | exact artifact digests and predecessor statement/subject bindings |
| final DBOM document | signed handoff manifest binding exact roots, heads, statements, and artifacts |
| one global schema | immutable core plus digest-pinned public or private organizational profiles |
| boolean-style verification | versioned report with per-check status and stable diagnostics |

## Historical evidence boundary

A v0.1 document can be preserved as an ordinary historical artifact and newly observed by a v0.2
origin statement. That proves only that the v0.1 bytes existed when the v0.2 signer observed them.
It does not retroactively establish:

- authentic v0.1 signatures;
- authorization of the historical signer string;
- completeness of the historical lineage array;
- byte bindings for historical intermediate data; or
- freshness of the historical record.

No compatibility mode may synthesize those missing guarantees.

## Migration sequence

1. Keep v0.1 producers and URLs clearly labeled historical while introducing v0.2 side-by-side.
2. Start new v0.2 histories at the real source boundary; do not translate only the terminal array.
3. Give each operation class an appropriate signing key and define authorization in receiver
   policy.
4. Move organization-specific requirements into digest-pinned profiles.
5. Require a signed handoff and independent expected manifest/head/artifact input at every trust
   boundary.
6. Retire v0.1 automation only after downstream consumers use v0.2 reports and negative tests.

The runnable migration target is [the v0.2 end-to-end demo](../demos/v0.2-end-to-end/README.md).
