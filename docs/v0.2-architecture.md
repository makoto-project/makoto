# Makoto v0.2 architecture

Makoto is a portable evidence layer for data, not a catalog, orchestrator, storage system, or
policy service. Its core is a small set of immutable JSON objects and exact verification rules.

## Evidence flow

```text
source bytes
    |
    v
signed origin statement
    |
    v
signed transformation statement(s) ---- digest-pinned private profiles
    |                                      | statement/predicate/artifact
    v                                      v
signed handoff manifest -------------- receiver schema catalog
    |
    v
bundle + receiver-owned policy + independent expectations
    |
    v
ALLOW or DENY + versioned verification report
```

Every origin or transformation is an in-toto Statement v1 payload carried in a DSSE v1
envelope. The payload is content-addressed by SHA-256 over its exact decoded bytes. A
transformation points to predecessor statement and subject digests, which produces a DAG that
supports linear pipelines, joins, splits, and multiple origins without rewriting earlier claims.

## Four separate questions

The verifier keeps four concepts separate because collapsing them creates false assurance:

1. **Integrity:** do artifact, statement, schema, policy, and manifest bytes match their digests?
2. **Authenticity:** are the DSSE signatures cryptographically valid for the configured keys?
3. **Authorization:** does receiver-owned policy allow those keys to make those claim types?
4. **Completeness and freshness:** does an authorized handoff bind the exact graph and artifact
   set, and does it match an independent expected manifest, head, artifact, nonce, or age rule?

A valid signature is not authorization. A connected graph is not proof that no branch was
omitted. A signed handoff is not fresh unless the receiver supplies an independent anchor.

## Organizational profiles

The Makoto core deliberately does not standardize every data team's metadata. A signed profile
reference pins a schema root, its complete external resource closure, target, criticality, and—
for artifacts—the subject and media type. The actual schemas may remain private. Verification is
offline and resolves only exact `(id, digest)` pairs from local catalogs.

Profiles use a closed Draft 2020-12-derived dialect. Portable string matching uses
`makotoPattern`, a bounded Thompson-NFA vocabulary with no backtracking host regular-expression
engine. Artifact validation currently supports exact JSON and NDJSON bytes; other formats need a
future versioned adapter contract.

## Cryptography and byte identity

- Artifact hashes cover byte zero through EOF with no normalization or reserialization.
- Statement hashes cover exact decoded DSSE payload bytes.
- DSSE signatures cover exact PAE bytes.
- v0.2 trust policy supports strict Ed25519 keys identified by SHA-256 of canonical RFC 8410
  SubjectPublicKeyInfo DER.
- Logical path NFC and full case folding use checksum-gated Unicode 15.0.0 tables vendored in the
  repository, not the host operating system's Unicode version.

Semantically equivalent JSON with different whitespace or key order is a different artifact.
Normalizing or converting data is a new transformation that produces new attested bytes.

Historical material and partition bytes do not become graph nodes. They remain content-addressed
evidence bound to signed statement subjects. Ordinary historical mappings are hashed whenever
their statement is authorized and manifest-listed, while reachability and exact-set completeness
remain separate checks. For partition pruning, a transformation binds a dataset-manifest subject
plus an `entryName`; the verified manifest member supplies the expected partition digest and
optional size.

The verification report has a closed diagnostic API. Each stable code is permitted only at the
step and owning check listed in
[`testdata/v0.2/diagnostic-map.json`](../testdata/v0.2/diagnostic-map.json), and its context is
validated by the code-specific branch of the verification-report schema. Human messages may
change; code, step, owner, context members, and deterministic ordering are compatibility surfaces.

## Trust boundary

Producer evidence includes statements, signatures, a handoff, and artifact bindings. It does not
get to choose receiver trust. Public keys, authorization rules, required profiles, and expected
handoff/head/artifact anchors come from receiver-owned inputs outside the producer bundle.

The verifier produces deterministic machine-readable diagnostics and never claims that a source
was truthful, a transformation really executed, the data is non-malicious, or metadata is secret.

The normative contract is [the v0.2 specification](../spec/v0.2.md).
